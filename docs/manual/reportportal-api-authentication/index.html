    Report Portal API authentication

    Reviewed against reportportal-main.zip on 11 November 2026.

    The production /api/login-options endpoint was also checked on 11 November 2026. It reports ssoEnabled: true and the organizations Microsoft authority. Whether SSO is selected for a particular user is resolved from the supplied e-mail domain, so Qvitr discovers the client ID and authority at sign-in time instead of storing them in the connection.

    Supported portal authentication

    The portal supports three client authentication paths:

    1. Personal API key in x-api-key. It is read-only and accepted only for GET endpoints. The key inherits the portal user's company access.
    2. Portal bearer token in Authorization: Bearer <token> or x-forecast-auth: Bearer <token>. It is returned by /api/verify-login-code and supports the API operations allowed for the user, including write endpoints.
    3. Microsoft Entra SSO. The client obtains a Microsoft ID token and posts it to /api/sso-login. The portal validates the token and returns the same portal bearer-token format as the e-mail-code flow.

    The generic Qvitr Microsoft Entra API token mode is intentionally separate. It obtains an Entra access token for an API scope and is suitable only when the target API validates Entra access tokens directly. Report Portal does not do that; use Portal session (email code + SSO) instead.

    Qvitr setup: portal session

    In API Workspace:

    1. Create or select a connection.
    2. Open Connection auth.
    3. Select Portal session (email code + SSO).
    4. Click Use Report Portal defaults, or configure:
    5. Base URL: https://rapporteringsportalen.teknigruppen.com/api/
    6. Authentication profile ID: report-portal
    7. Allowed origins: https://rapporteringsportalen.teknigruppen.com
    8. Request-code path: request-login-code
    9. Verify-code path: verify-login-code
    10. Login-options path: login-options
    11. SSO-login path: sso-login
    12. Desktop redirect URI: http://localhost
    13. Header: x-forecast-auth (preferred for Azure Static Web Apps; the backend also accepts Authorization)
    14. Prefix: Bearer
    15. Save the connection.
    16. Enter the user's e-mail address and choose either:
    17. Send code, then enter the received code and choose Verify and sign in; or
    18. Sign in with Microsoft. Qvitr checks /api/login-options?email=..., opens Microsoft sign-in only when SSO is enabled for the domain, and exchanges the ID token at /api/sso-login.

    The returned portal token is encrypted with Windows DPAPI for the current Windows user. It is not stored in the API definition, workbook or Qanvas file. The connection's allowed-origin list prevents the token from being sent to another host.

    Qvitr setup: read-only API key

    For unattended read-only refreshes:

    1. Select API key authentication.
    2. Use key/header name x-api-key.
    3. Use location Header.
    4. Store the tk_... value through Qvitr Secrets; do not place it in default headers or the document.
    5. Use only GET endpoints. The portal returns 403 API_KEY_READ_ONLY for write requests.

    The base address /api/ is not itself a data endpoint. Start with GET /api/companies to verify the connection. A 404 from /api therefore means only that no root endpoint exists. A 401 from /api/companies means the request reached the portal, but the key was not accepted. The key must match tk_ plus 64 lowercase hexadecimal characters and must be present, active and unexpired in the same database/environment as the deployed portal; its owner must also be active.

    The portal administrator creates keys with sec.usp_user_api_key_create after applying sql/2026-11-09_user_api_key.sql.

    Portal-side SSO requirements

    The portal must have:

    • SSO_ENABLED=true
    • SSO_CLIENT_ID=<Entra application client ID>
    • the tables and grants from sql/2026-11-09_sso.sql
    • an enabled tenant in sec.sso_tenant
    • an enabled e-mail domain in sec.sso_domain
    • an active matching user in sec.user_account

    For desktop Qvitr sign-in, add http://localhost to the same Entra app registration under Mobile and desktop applications and enable public-client flows. The existing web/SPA redirect URI remains in place for the portal browser client.

    If the domain is not configured for SSO, Qvitr leaves the e-mail-code option available. If Microsoft sign-in or the portal exchange fails, no Microsoft token is sent to a data endpoint and the user can use e-mail code instead.
