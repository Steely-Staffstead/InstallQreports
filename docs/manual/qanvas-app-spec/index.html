    Qanvas App specification

    Status: MVP in progress. The implemented first slice includes an Interactive app tile, document-level embedded app files, a script-only sandbox, filtered datasource input, semantic canvas theme roles, a built-in Source analysis app, the App designer with AI, and an allow-listed host action bridge. Direct network access and arbitrary SQL remain blocked. Export snapshots remain a later phase of this specification.

    Implemented MVP

    The current implementation provides a safe vertical slice of the architecture:

    • Interactive app is available from Add tile.
    • App definitions are stored in the root apps collection of the .qanvas document, while tile instances reference an appId.
    • Each definition contains logical index.html, styles.css, and app.js files; no sidecar workspace is required at runtime.
    • Apps execute in an iframe with sandbox="allow-scripts" and a restrictive content security policy. Network, parent DOM, filesystem, and persistent storage access are unavailable.
    • The App designer can declare named host actions for a saved API endpoint or a SQL Server stored procedure. App JavaScript sees only the action ID and calls qanvas.actions.execute(id, parameters); connection strings and secrets never enter the iframe.
    • A canvas Action tile can target an App tile on the same page and send a named command with a JSON parameter object. The app subscribes with qanvas.commands.on(name, handler); this does not grant extra host access.
    • SQL actions accept only a one- or two-part stored-procedure name. Arbitrary SQL, table-valued parameters and UDT parameters are rejected. Parameters are derived by SQL Server and the result is capped by the configured row limit.
    • API and SQL results may be returned to the app, replace a document-embedded local table, or append to an embedded table with the same columns. The rows are then saved inside the .qanvas file in the same format as other embedded Manual tables.
    • The host passes schema, bounded filtered rows, source metadata, parameter context, filters, and resolved canvas theme roles to the app. API sources can also opt in to a read-only structured JSON companion for hierarchical renderers while retaining their normal flattened table.
    • The built-in Source analysis app summarizes rows, columns, numeric fields, missing values, uniqueness, ranges, means, and coverage.
    • App properties allow the row limit and filtered-context behavior to be controlled. The selected Qanvas datasource uses the shared tile source control.
    • Embedded definitions and instances survive document serialization and reload.
    • Each app stores a bounded currentSpec plus the six most recent short design messages. Reopening the designer therefore restores the app's intent without embedding an unbounded AI transcript in the document.

    Purpose

    Qanvas App adds small, interactive business applications to a Qanvas document. An app can combine a purpose-built user interface with the document's existing data sources, measures, parameters, filters, navigation, update actions, theme, and export pipeline.

    The extension must preserve the central Qanvas properties:

    • one portable .qanvas file;
    • deterministic analysis after the app has been authored;
    • local and offline operation by default;
    • controlled access to business data and document actions;
    • consistent behavior in Edit, Presentation, and exported webpages;
    • safe failure isolation so an app cannot stop the rest of the report.

    Qanvas App is not intended to turn Qanvas into a general web hosting service or a complete software-development environment. It is an advanced visual and workflow type for bounded business applications.

    Product position

    A Qanvas App is the interactive layer in a living analytical document. Native Qanvas objects remain the preferred tools for charts, matrices, grids, forms, Gantt plans, and reusable report layouts. An app is appropriate when the user needs guided input, custom interaction, analysis orchestration, or a specialized visual that cannot be expressed naturally with existing objects.

    Typical solutions include:

    • budget and scenario simulators;
    • monthly-close and reconciliation controls;
    • source profiling and data-quality analysis;
    • project intake and approval flows;
    • pricing and quotation configurators;
    • guided forms and decision trees;
    • report portals and navigation hubs;
    • specialized calendars and planning tools;
    • variance investigation workflows;
    • customer-specific analytical tools.

    Goals

    1. Store the complete app with the Qanvas document without a required sidecar folder.
    2. Allow apps to read explicitly permitted data, measures, parameters, and filter context.
    3. Allow apps to invoke explicitly permitted Qanvas actions.
    4. Provide deterministic local analysis helpers for common statistical and data-quality tasks.
    5. Apply the canvas theme and respond immediately when it changes.
    6. Support AI-assisted creation and editing without making AI a runtime dependency.
    7. Keep apps interactive in Presentation and offline webpage export.
    8. Produce stable snapshots for PDF, image, and PowerPoint export.
    9. Maintain backward compatibility with documents that contain no apps.
    10. Expose clear permissions, diagnostics, and recovery behavior.

    Non-goals for the first version

    • npm, package installation, bundlers, or arbitrary build commands;
    • server-side application code;
    • unrestricted network access or API calls that do not use an explicitly saved connection and endpoint;
    • direct access to WebView, the host process, the file system, or the parent DOM;
    • direct database credentials or connection strings inside app code;
    • background execution after the Qanvas document is closed;
    • replacing native charts, tables, matrices, grids, forms, or Gantt;
    • a public application marketplace;
    • multi-user concurrent editing or a hosted application database.

    User experience

    Add an app

    The Add tile menu receives Interactive app. The first dialog offers:

    • Blank app;
    • Data analysis;
    • Form and workflow;
    • Simulator;
    • Navigation hub;
    • Create with AI;
    • Import portable Qanvas App.

    The result is a normal canvas tile with move, resize, header, theme, filters, links, undo, duplicate, and delete behavior. A full-page app is initially a normal app tile sized to the page. A separate page type is not required for the MVP.

    App designer

    The designer uses the application theme, while its preview uses the current canvas theme. Its primary workspace has two full-height resizable panes:

    1. Design with AI: an editable, persistent Current spec; a bounded recent change history; and a resizable change composer.
    2. Live preview: the running sandbox using the current canvas theme and source context.

    Logical files, source contract, theme API, bridge actions and permissions are available in a collapsed Advanced code, connections and permissions drawer. This keeps the common AI iteration workflow prominent while retaining direct code access for advanced users.

    The common workflow is:

    1. choose a template or describe the app to AI;
    2. grant only the required data and action permissions;
    3. bind sources, fields, measures, parameters, and actions;
    4. test in the sandbox preview;
    5. apply the app to the tile;
    6. verify Presentation and the required export formats.

    Properties pane

    The selected app tile exposes these groups:

    • Header;
    • App;
    • Data bindings;
    • Permissions;
    • Theme and appearance;
    • State;
    • Filters;
    • Interaction;
    • Export;
    • Diagnostics.

    The properties pane supports changing bindings and runtime settings. Source code and structural changes open the full designer.

    Status and errors

    An app shows a themed status surface for Loading, Ready, No data, Permission required, Error, and Disabled. Errors remain inside the app tile. The user can open diagnostics, reset app state, reload the app, or restore the previous app version without reloading the complete Qanvas document.

    Document model

    The .qanvas file remains one UTF-8 JSON document. Apps are permanent document content stored in a new root apps collection. The named files are logical files, not required physical files beside the Qanvas document.

  "app": {
    "appId": "app-budget-simulator",
    "view": "main",

      "amount": { "type": "measure", "name": "Revenue" },
      "year": { "type": "parameter", "name": "Year" }
    },
    "settings": {},
    "state": {},
    "statePolicy": "document"
  }
}

    Logical files

    Supported MVP file types are:

    • HTML;
    • CSS;
    • JavaScript;
    • JSON;
    • SVG;
    • PNG, JPEG, WebP, and GIF.

    Text is stored as UTF-8. Binary assets use base64 encoding. Each entry stores a hash for validation and deduplication. File paths are normalized relative paths; absolute paths, parent traversal, device paths, and URL-shaped paths are rejected.

    The first version should recommend a maximum of 1 MB for HTML, CSS, JavaScript, and JSON combined and 10 MB for the complete app. The limits should be settings, not assumptions in the renderer. Larger applications should display a warning before they are embedded.

    App definition and instances

    One app definition can be used by multiple tiles. Each tile has independent bindings, settings, and instance state. Editing the shared definition updates all instances after confirmation. Duplicate as independent app creates a new definition and app ID.

    Unused definitions are retained until explicitly removed or until the user runs Clean unused apps. Save must never silently delete an app definition.

    State policies

    An app instance supports:

    • none: state exists only until the tile reloads;
    • session: state lasts until the document closes and is not saved;
    • document: JSON state is saved in the tile;
    • source: durable records are stored in an explicitly permitted embedded source rather than opaque app state.

    Business records should use source. document is intended for compact UI state such as a selected tab, collapsed sections, or saved simulator inputs. Secrets must never be stored in app state.

    Import, page copy, and components

    Importing pages also imports app definitions referenced by the selected pages. ID collisions are resolved by content hash:

    • identical hash: reuse the existing definition;
    • different hash: create a new ID and remap imported tile references.

    Reusable components may reference an app definition. Exporting a component must include the referenced app and required assets, but not data the component does not already include.

    Runtime architecture

    Each app runs in its own sandboxed iframe. The proposed baseline is:

    <iframe sandbox="allow-scripts"></iframe>

    The app does not receive allow-same-origin, allow-top-navigation, forms, popups, downloads, or storage permissions in the MVP. The host builds the iframe document from the saved logical files and applies a restrictive Content Security Policy.

    The runtime uses postMessage with an unguessable per-instance channel token. Every message includes protocol version, app ID, tile ID, request ID, and channel token. The host validates origin context, message shape, permission, payload size, and current tile ownership before executing a request.

    Apps never receive references to host DOM objects, WebView host objects, connection strings, credentials, or unrestricted document JSON.

    Runtime lifecycle

    1. The tile creates a sandbox and sends qanvas.initialize.
    2. The app returns qanvas.ready with its protocol version.
    3. The host sends theme, bindings, locale, page, filter, and presentation state.
    4. The app requests permitted data or actions.
    5. The host publishes change events when relevant context changes.
    6. The app sends qanvas.renderComplete when stable for screen and export.
    7. The host disposes subscriptions, object URLs, workers, and temporary files when the tile is removed or rerendered.

    A handshake timeout shows an app error with Reload and Diagnostics actions.

    Temporary runtime files

    The desktop host may extract logical files into a content-addressed cache under the application's local cache directory when WebView requires physical files. The cache is not authoritative and must be reproducible from the .qanvas document. Cache removal cannot damage the app. Cache content must not be placed beside the Qanvas document unless the user explicitly exports an app workspace.

    Qanvas App API

    The public API is versioned. Apps request capabilities through the bridge rather than reading the parent application.

    const app = await qanvas.ready({ apiVersion: 1 });

    Context and theme

    await qanvas.context.get();
await qanvas.theme.get();
qanvas.events.on("themeChanged", theme => {});
qanvas.events.on("contextChanged", context => {});

    Context contains only non-secret values required by the app: tile ID, page ID, mode, locale, effective filters, dimensions, zoom, and presentation state.

    Theme returns resolved colors plus semantic roles, palette colors 1–8, fonts, spacing, and color scheme. The host also exposes the same values as CSS custom properties inside the sandbox.

    Data

    await qanvas.data.schema({ source: "finances" });
await qanvas.data.rows({
  source: "finances",
  offset: 0,
  limit: 1000,
  fields: ["period", "company", "amount"],
  filterContext: "effective"
});
await qanvas.data.summary({ source: "finances" });

    Data is paged and copied as structured values. The API does not expose the complete Qanvas document or source connection definition. Requests exceeding the granted row, field, source, or payload limits fail with a typed error.

    When an API source explicitly preserves its structured response, the app's initial source payload also contains structured, with value, rootPath, sizeBytes, availability and refresh metadata. This is a read-only companion to rows; it does not change the source schema or table behavior. Each selected source in sources has its own optional structured member.

    The app subscribes to data changes explicitly:

    qanvas.events.on("sourceChanged", event => {});
qanvas.events.on("filtersChanged", event => {});

    Measures

    const revenueByCompany = await qanvas.measures.evaluate("Revenue", {
  sourceId: "finances",
  groupBy: ["company_id"],
  maxGroups: 5000
});

// {
//   columns: ["company_id", "Revenue"],
//   rows: [["company-1", 1250000], ...],
//   totalGroups: 42,
//   truncated: false
// }

    The host evaluates measures through the existing Qanvas measure engine. Apps must not reimplement a business measure when the document already defines it. Only sources explicitly selected for the app can be evaluated. Source, page and tile filters are inherited automatically unless the app tile is configured to ignore filtered context. A measure binding can expose the same grouped result declaratively by using the Table value type and selecting an Evaluate per field in App designer.

    Parameters and filters

    const year = qanvas.parameters.get("Year");
await qanvas.parameters.set("Scenario", "Best case");
await qanvas.parameters.setMany({ Year: 2027, Scenario: "Best case" });
await qanvas.filters.get({ scope: "page" });
await qanvas.filters.apply({ filterId: "filter-123", values: ["Arendal"] });

    Writes use normal Qanvas undo, dirty-state, dependency, and rerender behavior. An app cannot create hidden global filtering side effects. Source-filter changes require a separate permission and visible confirmation.

    Navigation

    await qanvas.navigation.openPage({ pageId: "page-details" });
await qanvas.navigation.focusTile({ tileId: "tile-exceptions" });

    Navigation follows Presentation visibility and access rules. An app cannot open an external URL without an explicit link permission and normal Qanvas link handling.

    Actions

    Apps call action IDs, not internal application functions:

    await qanvas.actions.execute("refresh-finances", { showProgress: true });

    Canvas Action tiles can also send a one-way command to a specific App tile:

    const unsubscribe = qanvas.commands.on("zoomToRegion", parameters => {
  zoomToRegion(parameters.region);
});

    Configure the Action tile with Send command to App, choose the App tile, enter the command name, and optionally provide a JSON object. Commands stay inside the existing app sandbox and are also supported by exported webpages.

    The action registry should normalize current navigation and source-update behavior and support future workflows. Initial action types are:

    • navigate to page;
    • focus tile;
    • open parameters;
    • refresh selected source;
    • refresh all sources;
    • refresh selected source and dependent queries;
    • apply or clear a named filter;
    • run a Qanvas App command.

    The host owns confirmations, progress, cancellation, error handling, dirty state, and permission checks. Apps receive structured progress events and final status.

    Embedded-source writeback

    Writeback is restricted to explicitly permitted embedded local sources. Query, API, generated, linked read-only, and external database sources are not writable through this API. In the App tile properties, select an embedded source and grant only the operations the app needs. Read access follows the normal selected source permission; Add, Edit, Upsert, and Delete are separate grants.

    const current = await qanvas.tables.read("tasks", { limit: 5000 });

await qanvas.tables.insert("tasks", {
  taskId: "task-42",
  title: "Review exceptions",
  completed: false
});

await qanvas.tables.update(
  "tasks",
  { taskId: "task-42" },
  { completed: true },
  { expectedRevision: current.revision }
);

await qanvas.tables.upsert(
  "tasks",
  { taskId: "task-43", title: "Publish result", completed: false },
  { key: "taskId" }
);

await qanvas.tables.delete("tasks", { taskId: "task-42" });

    The host validates source selection, storage type, operation permission, column names, scalar value types, and optional optimistic revision before changing a row. Successful mutations increment the table revision, synchronize the portable JSONL payload, mark the Qanvas document dirty, and rerender dependent objects. Changes work in edit and desktop presentation views and are persisted when the .qanvas document is saved. Standalone exported webpages remain read-only because they have no document host to save back to.

    Canvas parameter bridge

    Canvas parameters are the first shared communication channel between App tiles and the rest of a Qanvas document. Access is granted explicitly per parameter in the App tile properties. Read and Change are separate permissions; enabling Change also implies Read. Calculated parameters are always read-only.

    const department = qanvas.parameters.get("Department");
await qanvas.parameters.set("Department", "Sales");
await qanvas.parameters.setMany({ Department: "Sales", Year: 2027 });

const unsubscribe = qanvas.parameters.subscribe("Department", (value, detail) => {
  console.log("Department changed", value, detail.previous);
});

    The host validates parameter existence, type, range and write permission before updating the document. A successful change recalculates calculated parameters, updates parameter-dependent tiles and notifies every running App tile that has read permission for the changed parameter. Exported webpages remain read-only.

    Analysis capabilities

    An app may analyze permitted loaded rows with deterministic JavaScript. Common and expensive operations should be provided by a host analysis service so apps do not repeatedly copy or recalculate the same data.

    await qanvas.analysis.profile({
  source: "finances",
  fields: ["period", "company", "amount"],
  checks: [
    "types",
    "missing",
    "distinct",
    "duplicates",
    "descriptiveStatistics",
    "outliers",
    "timeGaps"
  ]
});

    Standard analysis set

    • row and column counts;
    • inferred and declared data types;
    • missing, empty, invalid, and infinite values;
    • distinct values and cardinality;
    • duplicate rows or duplicate candidate keys;
    • minimum, maximum, sum, mean, median, and percentiles;
    • variance and standard deviation;
    • interquartile-range and configurable z-score outliers;
    • category distribution and concentration;
    • period coverage and missing time periods;
    • absolute, period-over-period, and year-over-year changes;
    • configurable reconciliation and threshold rules;
    • correlations for appropriate numeric fields;
    • largest positive and negative contributors.

    Analysis results are structured data with rule IDs, severity, evidence, affected row references, and summary text. They can be displayed in the app, written to an embedded source, or consumed by native cards, matrices, tables, and charts.

    AI may author rules and explanatory templates, but normal refresh must execute the saved deterministic rules without requiring an AI call. Optional AI-written summaries must be a separate user action with clear data-sharing behavior.

    Performance rules

    • Run analysis in a worker or host background task.
    • Cache results by source revision, effective filter context, fields, and check configuration.
    • Reuse Qanvas measure caches rather than evaluating the same dependency per row.
    • Use paging, column projection, and typed arrays for large numeric data.
    • Use sampling only when requested or when the result clearly labels it.
    • Recommend SQL-side analysis when the loaded result is incomplete or too large.
    • Cancel obsolete analysis when source, filters, or app configuration changes.

    Action workflows

    An app may orchestrate several registered actions while the host remains in control. A workflow definition is declarative and saved in the app manifest or the document action registry.

    {
  "id": "monthly-close-check",
  "steps": [
    { "action": "refreshSource", "source": "finances" },
    { "action": "runAnalysis", "profile": "monthly-close" },
    {
      "when": "analysis.errorCount > 0",
      "action": "navigate",
      "pageId": "page-exceptions"
    },
    {
      "when": "analysis.errorCount == 0",
      "action": "navigate",
      "pageId": "page-management-report"
    }
  ]
}

    The workflow runner provides:

    • visible current step and progress;
    • cancellation between cancellable steps;
    • confirmation before destructive or broad actions;
    • typed outputs available to later steps;
    • conditional branches;
    • one final rerender where safe;
    • a short audit entry containing time, action, result, and source revisions;
    • recovery guidance after partial failure.

    Arbitrary JavaScript cannot bypass the action registry by sending invented host messages.

    AI authoring

    AI creation is an authoring convenience, not part of the app runtime. Qanvas exports one app definition to an editable workspace:

    apps/app-budget-simulator/
  manifest.json
  index.html
  styles.css
  app.js
  assets/
QANVAS_APP_API.md
APP_REQUEST.md
validate-qanvas-app.cjs

    These are temporary or user-selected workspace files. Apply app changes validates and packages them back into the root apps collection. The workspace can be deleted after applying without affecting the Qanvas file.

    The same workflow supports Codex, Claude Code, Copilot CLI, and an external AI workspace. Provider-specific files must not become runtime dependencies.

    AI context

    The authoring package includes only:

    • the selected app and its current bindings;
    • the public Qanvas App API specification;
    • schemas for permitted sources, not credentials;
    • permitted measure and parameter names;
    • current canvas theme tokens;
    • screenshots explicitly attached by the user;
    • the user's request and validation instructions.

    Row samples are opt-in and bounded. The UI states exactly which schemas and data samples are included before export or submission.

    Validation

    The validator checks:

    • manifest and protocol version;
    • entry file and logical paths;
    • content hashes and duplicate paths;
    • file and total size limits;
    • prohibited URLs, APIs, HTML, and permissions;
    • declared versus used Qanvas capabilities;
    • source, field, measure, parameter, filter, action, page, and tile references;
    • theme variables and accessibility metadata;
    • HTML parsing and JavaScript syntax;
    • CSP compatibility;
    • UTF-8 and mojibake markers;
    • deterministic packaging order.

    Security model

    Permission principles

    • Deny by default.
    • Permissions are visible and editable before the app runs.
    • Permissions are based on stable IDs where available, with names shown to users.
    • Imported apps start disabled when they request unavailable or broader access.
    • Permission expansion requires confirmation.
    • A duplicated tile does not gain new permissions.
    • Export never adds permissions that the document does not already grant.

    Prohibited runtime capabilities

    The MVP blocks:

    • fetch, WebSocket, EventSource, and external resource URLs;
    • browser storage and service workers;
    • clipboard, camera, microphone, geolocation, notifications, and screen capture;
    • popups and top-level navigation;
    • dynamic code loaded from outside the embedded definition;
    • host objects, file paths, process execution, and shell commands;
    • direct database or API connections;
    • hidden credential fields and environment variables.

    Resource controls

    The host enforces limits for:

    • app package size;
    • bridge message and response size;
    • rows and fields per request;
    • total copied data per app session;
    • analysis duration and memory;
    • stored instance state;
    • event and action frequency;
    • render-complete timeout.

    Repeated violations disable the instance and show diagnostics without affecting the page.

    Document trust

    Opening a document containing an app shows its trust state. Apps created in the current document are trusted after validation. Imported or externally modified apps are validated and may require Enable app. A future version may support signed organization apps, but signatures are not required for the MVP.

    Theme and accessibility

    Apps receive semantic roles and resolved values:

    • text;
    • accent and on-accent;
    • surface;
    • header background and header text;
    • grid;
    • positive and negative;
    • colors 1–8;
    • application and canvas font families;
    • color scheme and preferred contrast.

    The runtime exposes these as --qanvas-* CSS variables. Apps should not copy resolved theme colors into permanent custom values unless the user explicitly chooses a custom color.

    Minimum accessibility requirements are:

    • keyboard access to every interactive control;
    • visible focus;
    • semantic labels and button names;
    • logical tab order;
    • sufficient contrast;
    • no color-only status indication;
    • reduced-motion support;
    • scalable layout at application and canvas zoom;
    • an accessible app title and description in the manifest.

    Edit, Presentation, and export behavior

    Edit mode

    Pointer mode selects and resizes the tile. An explicit Interact with app control or double-click enters app interaction. Escape returns to tile selection. This prevents an app from breaking normal canvas selection and drag behavior.

    Presentation mode

    The app is interactive immediately. Only permissions appropriate to Presentation are active. Editing or writeback remains opt-in per app and per embedded source, following the same principle as editable List and Grid objects.

    Offline webpage

    The export includes the validated runtime and referenced app definitions. The app remains interactive without Qanvas installed. Unsupported host actions are disabled with an explanatory message. Data included in the export follows the same presentation/export data rules as native tiles.

    PDF and image

    Qanvas waits for qanvas.renderComplete, fonts, images, and a short stability period before capture. Timeouts produce a diagnostic and a themed fallback instead of blocking the full export.

    PowerPoint

    The app is exported as a high-quality image with its canvas background rendered as a native PowerPoint shape where possible. The app is not editable as a live application in PowerPoint. An optional note can contain the app name and source Qanvas document reference.

    Versioning and compatibility

    The app runtime protocol, app definition, and Qanvas document version are separate concepts:

    • runtime: qanvas-app-v1 selects the bridge and sandbox contract;
    • appVersion tracks revisions of one app definition;
    • the root document version tracks Qanvas schema migrations.

    Unknown root properties continue to be preserved. Older Qanvas versions that do not support app tiles should show an unsupported-object placeholder rather than discarding the object during save.

    App edits participate in the normal document dirty state and Undo/Redo. Before a shared definition is replaced, Qanvas stores the prior definition in the undo entry. Optional named versions may be added later without becoming a prerequisite for normal editing.

    Diagnostics and observability

    The diagnostics panel shows:

    • app and runtime version;
    • granted permissions;
    • package size and file hashes;
    • current tile, page, source revisions, and filter-context hash;
    • handshake and render status;
    • recent bridge requests with duration and payload size;
    • analysis cache hits and misses;
    • action progress and last error;
    • console messages truncated to safe single-line summaries.

    Diagnostics must not reveal credentials, connection strings, hidden data rows, or unrestricted host paths. A support export requires user confirmation and shows exactly which metadata, logs, schemas, and samples it includes.

    Implementation plan

    Phase 0: schema and validator

    • Add the root apps collection and kind: app tile.
    • Preserve apps in open, save, Save as, Undo, duplicate, page import, and component import.
    • Add deterministic packaging, hashes, size checks, and reference validation.
    • Render a safe unsupported/loading/error placeholder.
    • Extend the Qanvas AI format guide and validator.

    Phase 1: sandbox and read-only apps

    • Add sandbox iframe and versioned message bridge.
    • Implement context, theme, schema, paged rows, measures, parameters read, filter context, and navigation.
    • Add blank, analysis, simulator, and navigation templates.
    • Add designer preview and properties.
    • Support Edit, Presentation, webpage, PDF, image, and PowerPoint snapshot.

    Phase 2: actions and deterministic analysis

    • Add normalized action registry and progress protocol.
    • Support selected/all source updates and dependent-query updates.
    • Add source profiling, descriptive statistics, duplicate/key checks, time gaps, outliers, and saved validation profiles.
    • Allow analysis results to populate an embedded source.
    • Add workflow sequencing, conditions, cancellation, and audit entries.

    Phase 3: controlled writeback and AI authoring

    • Add transactional embedded-source mutation.
    • Add app workspace export, validation, Apply, recovery copy, and provider-neutral AI instructions.
    • Add Create with AI and Edit app with AI flows.
    • Add app versions and restore.

    Phase 4: reusable organization apps

    • Add signed organization templates and a controlled catalog.
    • Add organization permission policies and trusted publishers.
    • Evaluate optional network connectors through host-managed actions rather than direct iframe networking.
    • Evaluate hosted collaboration separately from the portable file format.

    MVP acceptance criteria

    The first releasable version is complete when:

    1. A user can create an app tile from a template and save it in one .qanvas file.
    2. Reopening the file restores the app without a sidecar folder or AI service.
    3. The app follows canvas theme changes without saving resolved custom colors.
    4. The app reads only permitted source fields and measures using bounded paging.
    5. The app can read a parameter, change an explicitly writable parameter, apply a permitted page filter, and navigate to a permitted page.
    6. Invalid or unresponsive app code cannot stop canvas rendering or saving.
    7. Presentation and offline webpage export keep the app interactive.
    8. PDF, image, and PowerPoint exports capture a stable app state.
    9. Page import and duplication preserve or remap app references correctly.
    10. The validator rejects path traversal, external resources, prohibited APIs, undeclared capabilities, invalid references, and oversized packages.
    11. Keyboard navigation, focus, labels, and reduced motion pass the defined accessibility checks.
    12. Automated tests cover bridge permissions, malformed messages, timeouts, lifecycle cleanup, theme changes, data limits, import, save/reload, and all supported export modes.

    Open decisions

    The following decisions should be resolved during prototype work:

    1. Final package and per-file size limits.
    2. Whether text files remain directly visible in document JSON or use a compact encoded package representation.
    3. Whether session state should survive application restart.
    4. The first supported embedded-source mutation operations.
    5. The exact action registry format and stable action IDs.
    6. Whether app definitions can be shared across several open documents.
    7. Whether organization signing belongs in the first enterprise release.
    8. Whether external links are allowed independently of network access.
    9. The threshold where analysis should be moved to SQL or a host background engine.
    10. Whether a future hosted Qanvas service should use the same app package without changing the portable .qanvas contract.

    Recommended prototype

    The first prototype should be a Source analysis app because it exercises the most valuable integration without requiring writeback:

    1. Add the app tile and sandbox runtime.
    2. Grant read access to one loaded source.
    3. Read schema and bounded rows through the bridge.
    4. Calculate missing values, distinct counts, descriptive statistics, duplicates, outliers, and time gaps in a worker.
    5. Show a themed interactive analysis with field selection and severity filters.
    6. Allow a finding to navigate to a native detail page and set its page filter.
    7. Export the same result to webpage, PDF, and PowerPoint snapshot.

    This prototype validates portability, data access, analysis, theming, actions, sandboxing, and export before Qanvas accepts persistent app writeback or broader AI-generated workflows.
