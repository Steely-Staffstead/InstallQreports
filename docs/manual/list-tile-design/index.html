    List tile: design recommendation

    Decision

    Add a separate List tile for operational, editable rows. Keep Table as a simple read-only detail view and Matrix as the analytical table. Do not remove or silently convert the current Table tile: existing reports depend on its saved shape, and editing introduces permissions, validation, row identity, and write-back semantics that a reporting table should not acquire implicitly.

    The three tiles then have clear jobs:

    Tile Primary job Data behavior
    Matrix Grouped analysis, pivots, subtotals, drill and hierarchy Read-only
    Table Fast flat detail and export Read-only
    List Task lists and small operational registers Editable when embedded; linked sources are read-only initially

    Table and Matrix should continue to share rendering, formatting, sorting and field-picking code where practical. A later release may present Table as a "Flat table" preset of the Matrix renderer, but the saved kind: "table" must remain supported. Conversion should be explicit: Convert to Matrix or Create editable List snapshot.

    Reuse the existing data model

    Qanvas already has embedded/manual tables with typed columns, cell editing, lookups, calendar input, column resize/reorder, and automatic row creation. The List tile should be a focused view and workflow on top of that capability, not a second row database.

    Two modes are recommended:

    • Embedded list creates a private embedded manual source owned by the tile. The source contains the canonical schema and rows. An Expose as datasource option gives it a user-facing name and makes it available to cards, charts, matrices, filters, and other pages. The data is not copied when it is exposed.
    • Linked source references an existing Qanvas source. SQL, API, workbook, and generated rows remain read-only because they require a real write-back contract. A linked view may opt into editing when its source is another embedded List/manual table; every linked view then edits the same canonical rows instead of a cached copy.

    This is slightly different from the Gantt tile's tile-owned task array and published gantt:<tile-id> proxy. For a generic List, source-first ownership is cleaner because its data is already ordinary rows. The tile stores view and editing preferences; the embedded source stores rows and schema.

    Suggested stable identity:

    {
  "kind": "list",
  "sourceId": "list:8ee41e2a",
  "list": {
    "storage": "embedded",
    "exposeAsDatasource": true,
    "datasourceName": "Project actions",
    "columns": [
      { "field": "title", "width": { "mode": "percent", "value": 35 } },
      { "field": "status", "width": { "mode": "px", "value": 140 } },
      { "field": "due_at", "width": { "mode": "auto" } }
    ],
    "allowPresentEditing": false
  }
}

    The embedded source descriptor should carry ownerTileId and a stable source ID. Deleting or unpublishing it must warn about dependent visuals. A List must not consume its own published alias.

    Default task-list schema

    Start with a useful but small template. Users can remove optional fields or add their own.

    Field Type Behavior
    id UUID/text Immutable primary key; hidden by default
    line_no Integer Automatic display/order number
    title Short text Required primary description
    description Long text Optional multiline editor
    status Choice Open, In progress, Completed
    priority Choice Low, Normal, High
    owner Text or lookup Optional assignee
    due_at Date Shared date picker
    completed_at Date/time Optional; may be set when completed
    created_at Date/time Automatic, read-only
    updated_at Date/time Automatic, read-only

    created_by and updated_by should only appear when the host supplies a stable user identity. Otherwise they imply an audit trail that Qanvas cannot prove.

    Custom field types for version one:

    • Short text and long/multiline text
    • Integer, decimal, currency and percent
    • Boolean
    • Date and date/time, stored as ISO values
    • Choice with separate stored code and displayed label
    • Lookup with source, key field, display field, missing-value behavior and an optional manual code/label list

    URL, email, attachments, formulas, cascading lookups and write-back adapters fit later phases. A lookup stores the code; it never stores the display text as the authoritative value. Date fields use the existing shared calendar.

    List workflow

    • Add row creates a row below the current row. Enter commits the cell; Tab moves across fields and creates another row from the final editable cell.
    • Choice and lookup cells use a searchable dropdown. Date cells use the shared date picker. Long text can expand into a resizable editor while retaining an inline preview.
    • Required fields, numeric ranges, duplicate keys and missing lookup values are validated at cell and row level. Invalid rows remain visible and explain the error; they are not silently discarded.
    • Row commands are Duplicate, Delete, Move, Mark complete and Open details. Delete and schema/type conversions remain undoable or require confirmation.
    • Search, sort, filters, frozen columns and compact/comfortable row density use the same shared grid behavior as Table and embedded manual tables.
    • Column width is { mode: "auto" | "px" | "percent", value? }. Percent widths share the available area, pixel widths remain fixed, and Auto consumes the remainder with sensible minimums. Multiline rows can use Auto height or a configurable fixed/clamped height.

    Editing is enabled in normal Edit mode. Presentation editing is a separate, off-by-default option, matching Gantt. Web export should remain read-only until there is an explicit persistence target.

    Designer

    Use the established two-pane designer: properties on the left and a real live preview on the right. The dialog is movable and resizable. Compact group shortcuts remain visible above the property pane:

    • Data — Embedded/Linked mode, source, expose/name datasource
    • Fields — add/reorder fields, type, required/default value, lookup setup
    • Layout — widths, row height, density, multiline, frozen columns
    • Appearance — theme roles, header/cell typography, borders, badges
    • Interaction — add/delete/duplicate, Present editing, selection behavior

    Preview objects are navigation targets:

    • Click a column heading to focus that field and its width settings.
    • Click a value cell to focus that field's editor and formatting.
    • Click the toolbar, row action area, empty state or list frame to focus Interaction, Layout or Appearance respectively.
    • Keyboard focus moves to the selected property section, and the active preview target and shortcut use the same highlighted state.

    There is no Apply/Save button in the designer. Every valid change updates the tile/source model and preview immediately and participates in canvas Undo/Redo. Closing the designer only closes it. The document still uses the normal Qanvas Save command to persist the .qanvas file, so live designer updates do not pretend that the file has already been written to disk.

    Form view and inspector reuse

    The List tile also has a Form · one record view. This is a view of the same source and schema, not a second data store or a separate tile type. It is suited to test-case registration, issue intake, master-data maintenance, and any case where a wide row is easier to edit as a professional form.

    • The form supports 1–6 columns. Each column can use Auto, relative percent, or fixed pixel width. Row and column gaps and compact spacing are configurable.
    • Every visible field has column, column span, and row span. Labels can be above or to the left of controls.
    • Automatic controls follow the field type: date/date-time picker, checkbox, choice/lookup select, URL picker, numeric input, and multiline text.
    • Numeric fields can opt into a slider with min/max/step. Choice, lookup, and numeric values can opt into a badge when a display-only summary is preferred.
    • A navigator moves through the records that remain after source, page, and tile filters. Add, duplicate, and delete use the same permissions as the normal List view.
    • selectedRecordId is stable when rows are sorted or filtered. With followSelection, clicking a row in a table List updates Form views using the same source, including a form on another page when that page is opened.

    An inspector should be a presentation shell around this same form schema. It may be docked to the side or bottom, floating and movable, or opened on demand, but should not own its own rows or duplicate field configuration. An optional future Use form as inspector action can select a Form-view List definition and choose its placement. This keeps ad-hoc layout power while avoiding a second implementation of typed editors, validation, theming, and persistence.

    Delivery plan

    1. Add kind: "list", the embedded-source owner metadata, the task-list template, linked read-only mode, and datasource exposure.
    2. Reuse the manual-table cell editors for typed fields, lookup/manual lists, date picker, multiline text, widths, validation and inline row creation.
    3. Add the movable/resizable designer, property shortcuts, clickable preview, keyboard flow, Undo/Redo and Present-mode permission.
    4. Add search/filter/frozen-column polish, conversion commands and regression coverage for save/load, published-source dependencies and exports.
    5. Only after migration coverage is complete, consider hiding Add Table in favor of a Matrix flat-table preset. Continue rendering existing Table tiles.

    This approach has moderate implementation risk: most difficult primitives already exist, while the new work is ownership, UX composition, validation, conversion and lifecycle handling rather than another storage engine.
