    MCP sources in Qvitr

    Purpose

    Qvitr uses MCP in two separate phases:

    1. During design, AI may inspect configured MCP servers, sample read-only data and create a Qanvas solution.
    2. During refresh, Qvitr executes the saved source recipe directly. Refresh is deterministic and does not call AI.

    This separation keeps runtime inexpensive, predictable and available when no AI CLI is configured.

    Current foundation

    • MCP connections support Streamable HTTP and stdio transports.
    • Connection discovery records tools, resources and prompts.
    • Only tools annotated as read-only and non-destructive are enabled.
    • Configured MCP servers and enabled tools can be supplied to Codex, Claude and Copilot.
    • Query Workspace can list MCP resources and enabled tools as source candidates.
    • A saved MCP recipe can read a resource or call an enabled tool during preview and report refresh.
    • MCP responses retain structured JSON and receive a table projection for regular Qanvas visuals.

    Saved source contract

    {
  "connectionName": "Finance MCP",
  "sourceKind": "mcp",
  "mcpSource": {
    "Type": "mcp",
    "Operation": "tool",
    "ToolName": "financial_overview",
    "Arguments": {
      "company": "{{Company}}",
      "year": "{{Year}}"
    },
    "ResultPath": "$.rows",
    "Shape": "table",
    "PreserveStructuredJson": true
  }
}

    For a resource recipe, use Operation: "resource" and ResourceUri instead of ToolName and Arguments.

    The JSON recipe is currently also stored in queryText, which makes it visible and editable in Query Workspace and keeps it compatible with the existing source persistence path. mcpSource is the typed companion contract.

    Refresh sequence

    1. Load the named MCP connection from the local connection repository.
    2. Resolve Qanvas parameters in the resource URI or tool arguments.
    3. Verify that a tool is still in EnabledTools before calling it.
    4. Read the resource or call the tool.
    5. Select ResultPath when one is configured.
    6. Preserve the selected JSON as structuredData for App and HTML tiles.
    7. Project the selected result into a DataTable for tables, matrices, charts, filters and measures.
    8. Apply type overrides and report filters through the normal refresh pipeline.
    9. Replace the saved snapshot only after a successful refresh.

    Projection rules

    • An array of objects becomes a table using the union of object property names.
    • An array of scalar values becomes one value column.
    • A single object becomes one row.
    • Nested objects and arrays remain compact JSON strings in the table projection.
    • A result path should select the desired row array when the MCP response contains several branches.
    • The structured companion is limited to 5 MB. The table projection remains usable if that limit is exceeded.

    Security model

    • The Qanvas file stores the connection name and recipe, never credentials or access tokens.
    • Secrets remain in the Qvitr connection and secret stores.
    • Runtime tool calls require the tool to be explicitly enabled after MCP discovery.
    • Qvitr rejects tools that are not annotated as read-only and non-destructive.
    • Viewer refresh should be allowed only when the publisher permits refresh and the same named connection is installed for that Windows user.
    • A missing connection or rejected authentication must preserve the last good snapshot and display an actionable error.

    AI authoring contract

    AI may:

    • inspect discovery metadata and read-only samples;
    • choose a resource or enabled tool;
    • propose arguments, Qanvas parameters and a result path;
    • build visuals from the previewed schema;
    • save the validated recipe into the source.

    AI must not:

    • run as part of normal report refresh;
    • store connection secrets in the Qanvas document;
    • enable or execute destructive tools;
    • guess a production result path without validating it against a sample.

    Viewer and publishing behavior

    The published file should contain the selected saved-data snapshot according to the existing saved-data policy. Publish readiness should later report:

    • the MCP connection names required by the report;
    • whether each source has a usable saved snapshot;
    • whether Viewer refresh is permitted;
    • whether the current machine has the required connections and tool permissions;
    • whether the resource/tool and configured result path still validate.

    If refresh is unavailable, the Viewer can still use the snapshot. It should show a clear connection-required or sign-in-required state instead of clearing the data.

    Staged rollout

    Foundation — implemented first

    • Expose MCP connections in Query Workspace.
    • List discovered resources and enabled read-only tools.
    • Create and edit the JSON source recipe.
    • Execute MCP recipes during preview and refresh.
    • Produce both a table projection and structured JSON companion.

    Focused MCP source designer — next

    • Operation picker: resource or tool.
    • Tool argument form generated from discovery input schemas.
    • Qanvas parameter insertion.
    • Result-path picker over a sample response.
    • Table/structured shape preview and column types.
    • Connection, permission and stability validation before applying.

    Publishing and Viewer readiness

    • Required-connection manifest.
    • Viewer refresh permission.
    • Snapshot and authentication readiness checks.
    • Guided installation/sign-in message for missing connections.

    Advanced projections

    • Several named table projections from one MCP response.
    • Reusable projection mappings.
    • Schema drift diagnostics and optional column contracts.
    • Scheduled refresh when Qvitr later gains an approved background execution model.

    Maintenance checklist

    When extending MCP source support, keep these invariants:

    • AI remains design-time only.
    • Refresh remains deterministic.
    • Existing SQL, API, file and local-table source behavior is unchanged.
    • No secret is written to a Qanvas file.
    • Only enabled read-only tools can run.
    • The last successful snapshot survives refresh failures.
    • Structured and tabular consumers see data from the same MCP response.
